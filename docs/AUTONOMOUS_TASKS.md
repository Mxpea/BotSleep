# 有界目标程序与低模型调用执行

更新：2026-11-17。本文描述已接入源码的目标程序；离线覆盖和真实运行结果见 [TESTING.md](TESTING.md)。12 类入口已注册不等于每类目标都已在普通地图实服验收。

## 调用契约

daily/competition 默认启用 `run_survival_task`。模型选择一个目标，程序持续使用新观察计算下一步，直到目标得到验证、需要 AI 改变策略或到达中止边界。它复用现有原子技能，不新增游戏连接，不调用额外模型，不接收可直接执行的动作队列。

启用模型的普通 `daily` 可显式设 `survival.autonomy.local_opening: true`（默认关闭）。没有自定义目标、没有活动任务且当前观察支持工具开局时，harness 用同一控制器先启动一次 `starter_tools`。出结果或受阻后恢复原有决策；游戏 pending、模型槽未知及安全优先级不变。本地启动不伪造模型工具反馈，不适用于 competition。

实际工具目录按阶段路由：正常规划只暴露目标工具和必要安全/赛事管理工具，目标报告 `needs_ai` 后开放原子修复动作；解析同时检查本轮允许集合。不是只在 prompt 中写 prefer，也不是把全部原子工具一直暴露并假设模型会主动少调用。关闭 autonomy 时保留原有单步工具模式。

正常 daily 请求集合为 `run_survival_task/wait/eat_food/auto_sleep/retreat_from/fight_hostile`；competition 再加 5 个赛事管理工具。有 `task_id` 的 `needs_ai`、且没有 pending/unknown 时，每个目标最多接受 2 次生产原子修复提案，额度用尽后回到高层目录。wait、安全动作、赛事管理和解析格式 repair 不扣这项额度；提案是否成功仍由实际技能验证。明确的低血/饥饿受限食物情境只额外开放 `FOOD_ACTIONS`，不因此开放挖矿、建造或全部生产。`LLM_REQUEST.tool_mode/atomic_repair_remaining` 记录本轮路由和剩余额度，工具不在本轮允许集合时解析拒绝。

修复阶段也只开放当前任务需要的目录：按 12 类目标选择最多 10 个相关原子工具，再叠加目标与安全工具；缺少新鲜方块或实体候选时继续过滤采集、清叶、狩猎等入口。低血量食物限制优先，缺少任务元信息则退回保守的目标/安全集合。这样保留最近原生反馈与当前状态，同时避免一次加载全部技能 schema 撑爆请求字节预算；没有提高上下文预算或放松未知结果门禁。

```json
{"task":"gather","resource":"logs","count":16,"radius":32}
```

| 参数 | 约束 |
|---|---|
| `task` | 下表 12 个固定名称之一。 |
| `resource` | 仅 gather 必填：`logs/cobblestone/coal/raw_iron`。 |
| `item` | 仅 craft/smelt 必填，必须是程序支持的目标产物。 |
| `count` | 整数 1～64，默认 8；不使用布尔值代替整数。 |
| `radius` | 整数 4～64 格，默认 32；限制当前资源候选范围，不保证已经扫描完整球体或存在通路。 |

gather/craft/smelt 的数量是接受目标时库存基线之上的增加量。food 使用当前认可食物储备的绝对目标量；设施/工具目标使用各自 fresh 证据判定，不将 count 当作任意建筑尺寸或工具套数。仅 gather 接受 resource，仅 craft/smelt 接受 item；不接受模型指定的动作队列、任意坐标、命令或客户端接口。

| 目标 | 程序推进范围与完成证据 |
|---|---|
| `gather` | 采集或拾取目标材料；需要时补充木镐/石镐和工作台前置，以当前库存净增核验。 |
| `craft` | 为内置配方获取材料、准备工作台、逐次制作，以目标物品库存净增核验。 |
| `smelt` | 为指定产物准备现有支持的输入/燃料/熔炉，分开投料、等待、检查和收取；炉内产物不等于背包收益。 |
| `food` | 复用已绑定食物获取与加工动作，检查当前食物储备；原材料和挥击次数不自动算食物成功。 |
| `starter_tools` | 按日常工具任务板补齐基础工具及依赖，以当前物品/设施核验。 |
| `iron_tools` | 铁材料、熔炼、工具/盾/桶等任务板前置；现有有效装备证据可复用。 |
| `shelter` | 复用有界基地勘测、固定小屋逐块建造与几何检查，不保证照明或绝对防怪。 |
| `bed` | 获取受支持材料、制作、工作站位与双半床放置核验；没有材料来源或安全站位则明确受阻。 |
| `storage` | 复用箱子制作、放置及任务板所要求的当前储物证据。 |
| `farm` | 复用种子、成熟作物、耕地与种植等已绑定动作，以日常可再种植生产点证据核验。 |
| `recover_drops` | 记录当前观察到的掉落候选；拾取后须有真实库存增加，消失的实体不能当作已回收。 |
| `maintenance` | 持续复查日常条件并补缺，条件当前满足时等待再观察；不伪造永久完成。 |

住所目标会将当前已核验的施工站位转换为有界 `position_for_task`，每一步重新检查整个行走通道。需要换站位的已知、未写入失败不再冷却整个基地。最后屋顶施工后先按同一朝向对齐室内出口，再到门外放门；已有双半完整但打开的门先关闭。门前置要求同种木板 6 块，混合木板总数不能替代该条件；程序只补所选木种的缺口。备齐材料的四朝向及空背包纯木/混木离线测试已覆盖完整墙顶与门的几何核验；任意远距离选址、复杂整地和永久安全仍不在这一完成条件内。

日常住所可直接替换明确无碰撞的 `leaf_litter` 与 `short_grass`，它们不算支撑；积水、树叶、原木和实体障碍仍拒绝。放置后必须核实真实方块和库存消耗，门仍需双半、方向、铰链与关闭状态全部符合。木屋目标自行补齐木料和工作台，不需要先取得石器或熔炉。

目标程序放置工作台时也只使用与当前站位匹配的新鲜 `placement_candidates`，不再猜测脚边四格；没有候选时使用原有有界探索。目标格可为上述两种可替换植被，下方仍必须是真正的安全实心支撑，执行前再次读取。已核验住所内的工作台避开墙顶、旋转后的门道，并保留一侧双半床与其放置站位。放置结果未知时，技能和 harness 均保留 pending，不追加 stop 或换位置重放。

有完整新鲜证据、明确未执行写入的选址否决单独计数，保留已拒绝的中心和朝向，不消耗普通四次动作失败额度，也不清除之前的写失败。每四次否决尝试一次已观察的短距换位，最多 32 次勘测；原 8 次探索、128 总步数和 600 秒限制仍有效。复杂地形下，勘测加上材料与施工可能超过单目标预算，届时正常报告缺口并请求新规划，不承诺一次目标授权完成任意地点的小屋。

负向选址缓存随检查点保存，按服务器/账号/世界作用域、维度、死亡标记与生命代隔离，有效期 30 分钟，最多保留 128 个拒绝朝向和 32 个访问站点。新目标可避开仍有效的旧否决，步骤、失败和探索预算重新计数；旧记录没有产生时间时不猜测有效期。模型报告提供已搜区域与最近中心。缓存只提示哪里刚刚失败，不能证明任何位置安全。

至少四次当前勘测否决，或有效缓存已有四个不同中心被否决时，住所探索在合法候选中优先同层、其次下坡、最后上坡，同层优先附近同高站位更多的方向。它只影响排序，不授权新路线。住所允许超过 0.4 格且进入不同脚下格的短换位，避免漏掉自然落点偏离格心后的合法邻格；同格抖动仍不算探索。

`plan_shelter_preparation` 和 `prepare_shelter_step` 是住所目标内部能力，不加入模型工具。前者独立只读评估完整天然地板与出口、最多 8 个 `dirt/grass_block` 凸起；后者重新读取全场、站位、视线和全部敌人后，至多挖一格且不移动。禁止补地、架空、清建筑或树干、挖实际身体覆盖列及未知邻格；每步有 320 读/15 秒预算，写前预留后验读额度。只读已知否决可换朝向，缺块和网络错误不能当作确定的场地否决。任何 `prepared` 都必须再经过普通 `plan_shelter`，不能直接获得基地授权；未知写入不补发停止、挖掘或移动。

当前制作程序是明确的常用配方子集：58 项产物，包括 9 种木板/木门、16 色床、木石铁基础工具/锄、铁甲、盾、桶、熔炉、工作台、箱子、火把与面包。支持的熔炼产物有 10 种：铁锭、木炭、烤马铃薯以及已列出的牛/猪/羊/鸡/兔/鳕鱼/鲑鱼熟食。产物可识别不代表其所有原料来源都可自动获得；例如不能由此宣称钓鱼或兔子狩猎已经绑定。独立配方目录的 886 条记录不等于目标程序可规划和实服验证的 886 个配方。

## 模型与程序的分工

```text
模型返回一个 run_survival_task 调用
  → fresh 完整观察 + 参数/本地安全检查
  → 接受目标，保留原始 tool_call_id
  → 程序根据 fresh 观察计算一个子步骤
  → harness 记录该子步骤的 pending
  → 原有技能再次检查现场并执行，按库存/方块/位置核验
  → 保存真实结果和目标进度，重新观察后计算下一步
  → 完成 / 需要 AI / 未知 / 显式暂停或取消边界
  → 原始 tool_call_id 配对一次目标报告
```

普通子步骤没有伪造的模型工具调用，也不逐步请求 AI 批准。`AutonomousTaskController` 本身只有纯规划、证据和预算；`AutonomyRuntime` 接入原有单动作线程、串行模型 worker、本地安全层与 scoped journal。目标不扩大技能白名单，资源必须来自当前观察，不能用 terrain 的 nearest-per-type 代表点、旧记忆或模型猜测直接授权采集。

普通单步工具和最多 8 步的小批技能仍可使用。目标程序为保持每子步独立观察和意图记录，不把小批技能当作一个无边界的内部执行器。探索只使用已观察、近处、已知实心支撑的工作站位候选，并受探索预算限制。住所任务额外允许相邻直向上下 1 格，技能须复核完整身体扫掠、支撑、敌情和稳定落点；其他目标仍只使用同层探索。当前没有通用远路返家能力：超过 16 格或缺少当前基地证据时不能靠记忆授权施工，也不保证离开任意树冠或跨水。

自然台阶仍只发送一次移动。落地后遇到纯残余速度、短暂离地或高度未稳时，在原有 1.5 秒和 96 次总读预算内继续观察，每次检查敌情；需要连续稳定状态、实际目标格、脚下支撑与净空，才能确认成功。受伤、生命变化、控制输入、危险状态、缺失字段或读失败仍为未知结果；没有追加移动或停止。`landing_observation` 记录首末状态、待稳原因、样本数与结束原因，避免把所有后验问题混成同一个错误码。

## 配置与预算

```yaml
survival:
  operator_goal: "" # 可选的当前用户目标；例如优先采集所需木料并制作一把木镐。
  autonomy:
    enabled: true
    max_steps: 128
    max_seconds: 600
    max_local_failures: 4
    max_no_progress_steps: 8
    max_explore_steps: 8
```

这些限制属于单目标。全局步骤、运行时间、死亡预算和每个技能自己的 HTTP/动作预算仍然有效，目标授权不能延长它们。`max_explore_steps: 0` 禁止程序探索。配置默认启用；关闭后不会注册该目标工具给模型，原有单步模式保持可用。默认工具目录为 starter 9、daily 35、competition 40；禁用目标程序时 daily/competition 的模型请求目录分别为 34/39。

`operator_goal` 由本地配置给出当前用户期望，最多 1000 个可见字符；它不改变安全权限或伪造模型调用。需要采木后制作工具时，可把最终产物作为一个 `craft` 目标，程序会自动补齐所需原料与工作台，避免先单独问一次采木、再问一次每种配方。低血量的受限生产请求会同步收窄工具目录与目标参数，最终执行仍需通过本地检查。

已知失败可以记录目标冷却、换一个观察到的候选、处理真实掉落或补前置材料，不自动重发同一未知写入。库存、方块与站位证据没有进展时累计无进展次数；耗尽局部恢复或目标预算后给出 `needs_ai` 及真实缺口。`maintenance` 等待也受预算约束。不能把 `success=true` 的单步回包直接当作高层目标完成。

## 应急、中断与未知结果

近敌、已验证食物、生命、暮夜/睡眠等本地安全条件优先于生产，任务转为 suspended，安全策略不需再等模型。应急之后使用新观察重新计算子步骤，不从旧路线接着走。内部收盾是独立 pending 动作，不冒充目标采集成功；其结果未知时仍冻结目标。

树冠脱困使用内部 `canopy_escape`，不增加模型工具：每轮依据新读的脚下支撑、身体净空与相邻落点，只移动一个经过检查的中继步。树叶和撤离途中遇到的自然原木仍属于树冠，不能当成落地完成。单步最多上升一格、下降两格；没有完整地面路线时允许可核验的局部下降，最终必须观察到实际地面才能结束撤离。必要时仅清除一片已证明不承担当前支撑的邻列树叶，下一轮重新观察后再决定移动。读预算、历史落点去重、失败目标冷却和总步骤限制同时生效；不保证任意树冠可达。

骷髅、流浪者、沼骸和掠夺者的本地避险半径至少为 16 格，普通近战敌人使用配置半径；无盾时优先撤退。新鲜实体位置、拟前往的位置和执行期间的状态都要检查，不能只依赖最近敌人的一个名称。状态读到近敌但缺少坐标时先补充紧急观察，不向模型等待指令。

退路还需避免靠近其他射手；候选落点和实际第一步均检查多敌距离，执行前再次扫描。威胁消失后必须重新取得完整、新鲜且稳定的脚下证据：地面允许退出撤退，树叶或自然原木转入内部树冠恢复，不能永远留在过期近敌分支。主循环以不超过 0.1 秒的间隔调度生存 harness，实际观察、动作和失败冷却仍各自限速。死亡会改变本地生命序号，使旧路线与旧库存基线失效；unknown/pending 保持优先，不借生命变化清除未知写入。

地面撤退可把至多三格、同高直线且逐格复核的实心通道合为一次移动，减少一格一停；树冠、边缘、转角和升降保持单步。实际落地不等于脱险：全部已知敌人退出危险圈后，还需新实体扫描和稳定状态才能标记完成。已知到达但最终敌情字段不完整时保留撤退并要求新观察；传输或动作结果未知仍冻结，不能借此补发动作。

低血量但饥饿值不足 18 时不能靠原地等待自然回血。程序先处理已核验的食物，再在白天通过最多 8 个短距离、实心支撑的站位寻找食物；夜间延后搜索不消耗这项额度。局部搜索耗尽后，在生命大于 4、饥饿值至少 12、白天、地面稳定且附近无敌人的有限条件下，才允许模型选择小规模采木或木制品目标。程序子步骤再次核验生命、视野和距离，不为这种受限目标自动追逐掉落、清叶、挖矿或远行。没有真实库存增加仍报告失败，不能用方块消失冒充拿到材料。

传输超时、断线写入、非法回包、`dig_unconfirmed/action_unconfirmed` 或 `action_state=unknown` 保留原子动作 pending 并冻结目标，不能追加盲目 stop、攻击、放置或重新挖掘。各技能既有、有证据的有界恢复仍有效；例如未确认挖掘先在原技能内部复核，目标程序只消费它的最终真实结果。

撤退收到官方完整 `interrupted/cause=hurt` 回包时，只读复核后台空闲、同生命代/维度、稳定真实落点、支撑和身体净空；通过后以已终止的失败 `retreat_interrupted` 交回本地重新规划，不冒充到达原目标。缺少回包或稳定证据仍为 unknown，不追加 stop 或移动。

重启恢复的是目标与证据，不是待执行队列。保存的未确认子步骤不能自动重放；显式 resume 后须取得 fresh、完整、ready/alive/idle 观察，才能放弃旧未知目标并要求新规划。放弃不代表旧动作已证明未发生，历史未知结果与最近证据仍需保留。普通取消不能自行清除 unknown。模型远端 unknown 与游戏 pending 是独立状态；resume 不等于解除模型门禁。

正常运行只给原生目标调用一次配对报告。显式暂停若先关闭该调用，会以部分/暂停结果报告，之后续接原目标也不再对同一 call_id 重复反馈。完成和升级报告不代替原子结果、库存或服务器 advancement 的证据；赛事计分仍由赛事模块负责。

## 状态与监控

公开 `task_execution` 包含：`task_id/task/status/args`、`progress`、`current_step`、`steps/max_steps`、`local_recoveries`、`emergency_interruptions`、`ai_escalations/last_escalation_reason`、`reason/fresh/updated_at` 和最多 8 条 `recent_results`。状态为 `idle/running/suspended/completed/needs_ai/unknown/cancelled`。它不同于日常 13 项证据任务板和 competition 赛事目标。

`model_planning_rounds` 是真实启动模型规划 worker 的轮次；同一轮格式修复可能有多个 HTTP 请求。`model_calls_avoided` 表示已授权目标下程序选出的子步骤数，页面标为“程序子步骤”；它不是成功数，也不是节省费用的实测数据。事件和心跳携带完整快照，监控只展示发布值，不重复累加，不根据进度猜测完成。详见 [MONITORING.md](MONITORING.md)。

两项计数随同 API/账号/world_id 检查点累计，重启不归零；本次登录的真实 HTTP 请求请数本次会话的 `LLM_REQUEST` 事件。原子修复额度存在当前规划器实例中，重启需先经过既有恢复门禁。

## 验证与未覆盖范围

离线测试使用变化的内存库存、方块、熔炉槽位和实体来验证前置链与结果，不以固定成功回包代替效果。运行时回归检查原生反馈配对、游戏 pending、安全抢占、显式恢复、预算和内部收盾；页面测试检查未知值、脱敏、重复事件与实际脚本渲染。

没有因此新增通用建桥、游泳、无限树冠脱困、村民交易、下界流程、末地战斗、动态 Markdown skill 加载或语义 compact/handoff。无需末影龙的普通日常生存也仍会遇到安全地形、原料和视野限制。真实启动、某个原子动作成功、某个目标完成与全部 12 类实服验收是四个不同结论，实际状态以 [TESTING.md](TESTING.md) 为准。
